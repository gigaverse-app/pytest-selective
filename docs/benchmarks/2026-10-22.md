The two primary scenarios change only a comment in an existing test, so selection
changes but test behavior does not. Each full control uses `test:full` on the same
PR head and checked-out merge commit after the selective run finishes.

## Method and limits

- **Elapsed** is workflow creation to the last executed job's completion, including
  queue/dependency waits. **Runner-seconds** sum executed-job start-to-completion
  intervals, including setup and cleanup. They are not billed/rounded minutes or
  dollar estimates. Skipped jobs contribute zero, even when GitHub gives their
  records reversed timestamps.
- All comparisons use attempt 1 and successful completed runs/jobs. In-progress,
  failed and cancelled attempts are excluded. The exporter captures an explicit
  attempt so a later rerun cannot silently replace the measured jobs.
- Same PR heads: Due `6da506c27a66f3776b804bab4542d435d42e27ca`;
  pytest-obligation `967b4037999c7ca53414936fd2f9df4c77158622`.
  Checkout logs also confirm matching merge commits across each pair:
  Due `8fa75474d577a87877d84aa3a258d73980573573`;
  pytest-obligation `ac1243e80632ce996e652f71dc48b7f09bfe8c35`.
- One sequential pair per scenario, selective first. There is runner/cache/order
  noise: Due's identical standalone-export step took 81s selective versus 64s
  full, and its locked library step took 73s versus 58s. Do not interpret these
  observations as stable average savings or extrapolate to every PR. Shared
  runtime/plugin changes still select all lanes.
- The controls compare enabled selection with its full-suite override after
  adoption. Both include planner overhead; this is not a pre-adoption historical
  comparison. Measurement-only comments are closed without merging.

Reproduce the raw timing export with authenticated `gh` and Python 3.11+:

```bash
python scripts/measure_ci_runs.py gigaverse-app/pytest-obligation \
  39843219042 39843423688 --output obligation.json
python scripts/measure_ci_runs.py gigaverse-app/due \
  39843214916 39843954591 --output due-ci.json
```

The script makes read-only GitHub API requests. It checks success, completion and
matching head SHAs; merge-checkout identity is a separate check of the checkout
logs, because GitHub's run `head_sha` denotes the PR head, not the tested merge.

## Additional skips with preservation checks

[Recorded single-file replays](2026-10-22-input-replays.json) use real repository
Git trees, changing only a comment in each listed file. Compare the original
config at the recorded base with the proposed config using
`python -m pytest_selective.ci --repo REPO --config CONFIG --base BASE --head HEAD`.
They prove these lane decisions for the audited snapshots, not runtime speedups:

| Input | Before | After |
| --- | --- | --- |
| Due books/catalog/documents model or adoption-report checker | Integration + widgets | Integration |
| Due shared integration process helper | Integration only | Integration + widgets (missing dependency repaired) |
| Due settings, Celery bootstrap, widget scripts/models | Integration + widgets where applicable | Preserved |
| Due profiling bootstrap | Widgets | Preserved |
| pytest-obligation package README or package docs | Every test lane | Build/lint/types remain; live lanes skipped |
| Executable root README demo tape/environment | Demos | Preserved |
| Shared runtime/plugin in either consumer | Every test lane | Preserved |

Due's widget settings explicitly install only the standalone widget app. The
benchmark uses shared settings/Celery bootstrap, widget scripts and a shared
subprocess helper, all of which remain explicit inputs. Package/shim inputs and
widget assets/migrations also remain. New dynamic/cross-app dependencies must be
declared in the same PR.

pytest-obligation package documentation is packaging content, not a live-test
input. Build still validates distributions and installed-wheel compatibility and
identity. Root executable demo files remain explicit test inputs. Both consumer
PRs preserve every execution command, matrix, service and evidence validator;
workflow diffs only update the immutable planner action pin. Config changes
intentionally trigger full CI before adoption.
