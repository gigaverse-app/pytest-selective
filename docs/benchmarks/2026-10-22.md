# CI selection measurements: 2026-10-22

## Compiled coverage runtime

[Run 39848431314](https://github.com/gigaverse-app/pytest-selective/actions/runs/39848431314)
passed 521 tests on Windows 3.11 but spent 238 seconds in pytest and warned
`No module named 'coverage.tracer'`. The locked coverage 7.17.0 artifact list
contained no CPython 3.11 wheel, so it installed the pure-Python fallback.
Refreshing the package's lock metadata found the now-available compiled wheel
without changing the coverage version. A clean locked Python 3.11 install
reproduced the missing import before the refresh and loaded `coverage.CTracer`
after it. The same refresh includes CFFI platform wheels, avoiding an unnecessary
local source build. CI records its coverage runtime on every matrix lane.

This proves the runtime repair, not a fixed speedup percentage. The full platform
matrix and coverage collection remain enabled; compare subsequent measured runs
before attributing their timing difference entirely to the tracer.

These are successful GitHub Actions runs, not savings inferred from test counts.
The primary scenarios change only a comment in an existing test, so selection
changes but test behavior does not. A third pair changes only an HTML comment in
the package README after the documentation-input narrowing was merged. Each full
control uses `test:full` on the same PR head and checked-out merge commit after the selective run finishes.

## Method and limits

- **Elapsed** is workflow creation to the last executed job's completion, including
  queue/dependency waits. **Runner-seconds** sum executed-job start-to-completion
  intervals, including setup and cleanup. They are not billed/rounded minutes or
  dollar estimates. Skipped jobs contribute zero, even when GitHub gives their
  records reversed timestamps.
- All comparisons use attempt 1 and successful completed runs/jobs. In-progress,
  failed and cancelled attempts are excluded. The exporter captures an explicit
  attempt so a later rerun cannot silently replace the measured jobs.
- Same PR heads: Due `6da506c27a66f3776b804bab4542d435d42e27ca`;
  pytest-obligation `967b4037999c7ca53414936fd2f9df4c77158622`.
  Checkout logs also confirm matching merge commits across each pair:
  Due `8fa75474d577a87877d84aa3a258d73980573573`;
  pytest-obligation `ac1243e80632ce996e652f71dc48b7f09bfe8c35`.
  The later README pair uses head `669dcfb3923366fad9477dcd8aa5800403e7028b`
  and checked-out merge `99129f6e9cb6fb41d7fb769b1ec2b3e88ec0f9ec` in both runs.
- One sequential pair per scenario, selective first. There is runner/cache/order
  noise: Due's identical standalone-export step took 81s selective versus 64s
  full, and its locked library step took 73s versus 58s. Do not interpret these
  observations as stable average savings or extrapolate to every PR. Shared
  runtime/plugin changes still select all lanes.
- The controls compare enabled selection with its full-suite override after
  adoption. Both include planner overhead; this is not a pre-adoption historical
  comparison. Measurement-only comments are closed without merging.

Reproduce the raw timing export with authenticated `gh` and Python 3.11+:

```bash
python scripts/measure_ci_runs.py gigaverse-app/pytest-obligation \
  39843219042 39843423688 --output obligation.json
python scripts/measure_ci_runs.py gigaverse-app/due \
  39843214916 39843954591 --output due-ci.json
python scripts/measure_ci_runs.py gigaverse-app/due \
  39843214915 39843954580 --output due-widget.json
python scripts/measure_ci_runs.py gigaverse-app/pytest-obligation \
  39845887127 39845989456 --output obligation-docs.json
```

The script makes read-only GitHub API requests. It checks success, completion and
matching head SHAs; merge-checkout identity is a separate check of the checkout
logs, because GitHub's run `head_sha` denotes the PR head, not the tested merge.

## Additional skips with preservation checks

[Recorded single-file replays](2026-10-22-input-replays.json) use real repository
Git trees, changing only a comment in each listed file. Compare the original
config at the recorded base with the proposed config using
`python -m pytest_selective.ci --repo REPO --config CONFIG --base BASE --head HEAD`.
They prove these lane decisions for the audited snapshots, not runtime speedups:

| Input | Before | After |
| --- | --- | --- |
| Due books/catalog/documents model or adoption-report checker | Integration + widgets | Integration |
| Due shared integration process helper | Integration only | Integration + widgets (missing dependency repaired) |
| Due settings, Celery bootstrap, widget scripts/models | Integration + widgets where applicable | Preserved |
| Due profiling bootstrap | Widgets | Preserved |
| pytest-obligation package README or package docs | Every test lane | Build/lint/types remain; live lanes skipped |
| Executable root README demo tape/environment | Demos | Preserved |
| Shared runtime/plugin in either consumer | Every test lane | Preserved |

Due's widget settings explicitly install only the standalone widget app. The
benchmark uses shared settings/Celery bootstrap, widget scripts and a shared
subprocess helper, all of which remain explicit inputs. Package/shim inputs and
widget assets/migrations also remain. New dynamic/cross-app dependencies must be
declared in the same PR.

pytest-obligation package documentation is packaging content, not a live-test
input. Build still validates distributions and installed-wheel compatibility and
identity. Root executable demo files remain explicit test inputs. Both consumer
PRs preserve every execution command, matrix, service and evidence validator;
workflow diffs only update the immutable planner action pin. Config changes
intentionally trigger full CI before adoption.

Implementation: [Due #68](https://github.com/gigaverse-app/due/pull/68),

## Why the four repositories felt slow

A live audit on the same evening found distinct costs, not evidence of one shared
runner-capacity stall. Most sampled Due/obligation/selective jobs started 2–3s
after job creation. CI-esta had noticeable 5–22s waits between its short jobs.
These observations do not rule out transient queues outside the sampled runs.

| Repository and run | Observed bottleneck | Safe response |
| --- | --- | --- |
| [Due full control](https://github.com/gigaverse-app/due/actions/runs/39843954580) | 624s Chromium/system install in one job; baseline CPU profiling 430s plus wall profiling 135s, after a 213s browser benchmark | Narrow unrelated widget inputs; browser-launch probe with dependency-install fallback in [Due #67](https://github.com/gigaverse-app/due/pull/67) |
| [pytest-obligation full validation](https://github.com/gigaverse-app/pytest-obligation/actions/runs/39844677429) | Due conformance step 256s plus independent library controls 79s; Wagtail 165s, Saleor test step 157s, Prefect tests 156s | Skip complete unrelated lanes; preserve complete conformance guarantees when selected |
| [pytest-selective platform timings](https://github.com/gigaverse-app/pytest-selective/actions/runs/39846195007) | Git-heavy tests are much slower on Windows: clone-cache control 7.33s vs Linux 0.51s; graph-cache pruning 6.81s vs 0.41s | [#7](https://github.com/gigaverse-app/pytest-selective/pull/7) cancels superseded PR runs and records slow tests; [#9](https://github.com/gigaverse-app/pytest-selective/pull/9) skips docs-only matrices while retaining code-change platform coverage |
| [CI-esta extraction validation](https://github.com/gigaverse-app/ci-esta/actions/runs/39845148497) | Tests 37s and compatibility 38s, but five sequential stages and admission waits stretch workflow to 143s; reporting is last | Its [observer workflow](https://github.com/gigaverse-app/ci-esta/pull/3) moves measurement outside the validation path; do not remove evidence gates to shorten a clock |

The Windows logs identify slow Git/clone/CLI controls; they do not prove a single
OS-level cause or justify removing cross-platform tests. Future optimization
should measure fewer redundant Git subprocesses or fixture setup while retaining
real repository behavior. CI/config/dependency edits intentionally trigger full
validation, so adoption PRs cannot demonstrate the normal docs-only fast path.
