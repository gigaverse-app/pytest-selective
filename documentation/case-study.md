<h1>Thirty Thousand Tests</h1>
<p class="lede">Gigaverse runs two backend repositories with very different shapes. Over five and a half months, with coding agents writing much of the code, their test suites grew from 9,177 test functions to 30,159. This case study shows what we did to keep CI fast and on budget, what it bought, what it cost, and where the gains stop. The tooling that came out of it now ships as two open-source projects, <b>pytest-selective</b> and <b>CI-esta</b>.</p>
<div class="repos">
<div class="repo" style="--c:#F97316"><b>The Django monorepo</b><span>One large Django application with a Postgres database, Celery work and many HTTP endpoints. Nearly every test imports the same settings, models and app registry, so one change can easily reach the whole suite.</span></div>
<div class="repo" style="--c:#0EA5E9"><b>The microservices repo</b><span>About two dozen independently deployed Python services: Kafka consumers, Prefect workers and FastAPI APIs sharing a common package. A change usually touches one service, but tests are expensive to set up.</span></div>

<span class="eyebrow">What changed</span>
<h2>The suites tripled. The wait didn't.</h2>
<p>Tests were added every week across both repositories and the shared CI library that later became pytest-selective and CI-esta. The Django monorepo's suite grew fifteenfold. Its absolute wait climbed from under 4 minutes in June to over 8 in September and again in mid-October, and has since come back to about 6. The microservices repo's wait fell from about 5 minutes to 4 while its suite doubled.</p>

<span class="eyebrow">What it cost</span>
<h2>Spend grew with the suites. Cost per test fell.</h2>
<p>Agent-assisted work multiplied the number of pull requests, and each one is checked against a much larger suite. Billed minutes per merged PR fell by almost half after August and have held near 150–180. Normalized for suite size, billed dollars per merged PR fell from August to October: 25.7¢ → 18.3¢ per 1,000 tests in the monorepo (−29%) and 20.5¢ → 12.6¢ in the microservices repo (−38%).</p>
<p>In the microservices repo the savings were partly reinvested. September brought cost per 1,000 tests down to 9.5¢, less than half of August. In October about a quarter of that saving went back into speed: the remaining full runs moved to 16-vCPU runners (shard step 269s → 161s). The critical path per 1,000 tests then fell 29%, from 0.275 to 0.194 minutes, while cost settled at 12.6¢, still 38% below August.</p>

<section id="how">
<div class="head">
<span class="eyebrow">How</span>
<h2>Six chapters</h2>
<p>Each chapter made the next one safe. A flaky suite can't be trimmed to the tests a change reaches, and a selection nobody can explain won't be trusted to skip work.</p>
</div>
<div class="chapters"><article class="ch" style="--c:#F97316"><div class="ch-head"><span class="ch-n">1</span><div><h3>Make red mean something</h3><span class="when">May – June</span></div></div><p>Concurrent runs got their own database and cache, shared services were stubbed, and flakes were fixed at the cause. Coverage was measured for the first time, and the endpoints the performance work would touch were pinned with reviewed golden tests before anyone changed them.</p><ul><li><span>a database and Kubernetes job per CI run, so concurrent PRs stopped colliding</span></li><li><span>test database restored from a committed schema dump: setup <b>24.6s → 1.9s</b></span></li><li><span>hermetic tests moved off the cluster: feedback <b>~4m52s → ~2m7s</b></span></li><li><span>retry-to-green on <span class=mono>main</span>: <b>8 of 15 runs → 0 of 25</b></span></li><li><span>first coverage baseline: <b>54.6%</b>, about 70% a month later</span></li></ul></article><article class="ch" style="--c:#F97316"><div class="ch-head"><span class="ch-n">2</span><div><h3>Make each test cheaper</h3><span class="when">July</span></div></div><p>Profiling showed setup, not assertions, dominated. <div class="tool" style="--c:#38BDF8">
<div class="meta">pytest-selective · <a href="https://pytest-selective.readthedocs.io/en/latest/">docs</a> · <a href="https://github.com/gigaverse-app/pytest-selective">GitHub</a></div>
<div class="pitch">Run affected Python tests. See why they matter.</div>
<ul>
<li>Builds an import graph from both sides of a Git change and selects the test files it can reach, with an explanation for each choice.</li>
<li>Non-Python inputs are declared beside the code that reads them, and a file-read recorder audits what was missed (monorepo: 0 undeclared inputs in 22,891 reads).</li>
<li>Conftest, plugin or global inputs select everything. Missing proof means the full suite runs.</li>
<li>Runs as a pytest plugin, a pre-collection runner, or GitHub Actions that also skip unaffected CI lanes.</li>
</ul>
</div>
<div class="tool" style="--c:#FB923C">
<div class="meta">CI-esta · <a href="https://ci-esta.readthedocs.io/en/latest/">docs</a> · <a href="https://github.com/gigaverse-app/ci-esta">GitHub</a></div>
<div class="pitch">Let proven work rest. Measure the rest.</div>
<ul>
<li>Reports every run's gate latency, critical path, step timings and runner cost as a PR comment, JSON and Prometheus metrics.</li>
<li>Reuses validation that already passed on the same tree through completion receipts, behind a strict aggregate gate.</li>
<li>Plans shards from learned test timings, caches Python and Bun environments safely, and reruns earlier failures first.</li>
<li>Ships about 28 composable GitHub Actions, including security scans and a Bun test-selection adapter.</li>
</ul>

<section id="methods">
<div class="head">
<span class="eyebrow">Methods and limits</span>
<h2>How the numbers were made</h2>
</div>
<div class="methods">
<div><b>Per 1,000 tests</b><span>Every normalized figure divides by the test-function count on <span class="mono">main</span> at the end of that week or month, not by tests executed, which selection deliberately shrinks.</span></div>
<div><b>Test counts</b><span><span class="mono">git grep "def test_"</span> over test modules on each repository's <span class="mono">main</span> at the end of each week. Parametrized cases count once, so collected test counts are higher.</span></div>
<div><b>Wait</b><span>GitHub check-suite timestamps on the final commit of 1,367 microservices and 1,933 monorepo merged PRs: from the push's first workflow to its last gating check, with queue time included. Weeks with fewer than 10 PRs are dropped.</span></div>
<div><b>Full-suite baseline</b><span>Each week's 90th-percentile summed test time from about 40 sampled runs (Aug 10 onward, inside the 90-day artifact window), plus the median non-test overhead. It keeps today's per-test speed-ups, so it understates the original cost. Monorepo full suite in the week of Nov 2: 3,007s of test time; microservices: 2,002s.</span></div>
<div><b>Selection</b><span>Selected and total test files from each run's <span class="mono">test-impact-explanation</span> artifact, available from the week of Nov 2. Earlier weeks use the share of summed test time as a proxy.</span></div>
<div><b>Cost</b><span>The organization billing usage API by repository and day, all workflows included, divided by merged PRs (a crude denominator, because pushes per PR vary). Per-run dollars come from CI-esta's estimate in each run: rounded minutes per job times that runner's rate. Test-job dollars sum only the jobs that plan, run or report tests.</span></div>
<div><b>Chapter figures and benchmarks</b><span>Chapter figures were measured in the pull request that made each change. Benchmarks are quoted from the projects' published pages. Single paired runs are not averages, replays are labelled as such, and speed-ups are never summed, because they overlap.</span></div>
</div>
